# 要求仕様書: `goose-sdd --system` コマンド
## 概要
`goose-sdd --system <intent>` は、開発者がプロジェクト全体の高レベルな方針・ルールを自然言語で定義・更新するためのコマンドである。本コマンドは、人間の「理想（Intent）」をAIが解釈し、**`docs/sdd/` ディレクトリ配下にある複数のシステムドキュメント（プロダクト背景、システムコンセプト、アーキテクチャ、プロジェクトルール、ドメイン用語集など）から適切なものを特定し、そこに内容を反映させる、トップダウン型（処方的）のアプローチ**を担う。
## 背景・目的
ソフトウェア開発において、ドキュメントは一度作成されると、その後のコード変更に追従できずに陳腐化（Dead Docs）しやすい。このドキュメントと実装の乖離を手動で同期し続ける作業は、開発者にとって大きな負担となっていた。
本コマンドの目的は、この問題を解決するための中核的な機能を提供することにある。開発者が持つ「システムはどうあるべきか」という設計思想やルールを、まず `docs/sdd/` 配下のドキュメントに「唯一の信頼できる情報源（Source of Truth）」として記録する。これにより、ドキュメントを常に最新の「理想」の状態に保ち、コードとドキュメントの乖離を検知・修正する開発サイクル（The Negotiation Loop）の起点とする。
## ユースケース / ユーザーストーリー
### ユースケース1: プロジェクトの初期セットアップと背景定義
-   **利用者**: テックリード、またはプロジェクトの初期設計を担当する開発者
-   **状況**: 新しいプロジェクトを開始するにあたり、プロダクトのビジネス背景と目的を定義したい。
-   **操作例**: `goose-sdd --system "このプロダクトは、開発者のドキュメント更新負担を軽減し、常に最新のシステム設計ドキュメントを維持することを目的とする。"`
-   **結果**: AIが意図を解釈し、`background.yaml` レシピの文脈で `docs/sdd/00_product_background.md` に関連内容が記述・生成される。
### ユースケース2: システムコンセプトの定義
-   **利用者**: システムプランナー、プロダクトオーナー
-   **状況**: 定義されたビジネス背景に基づき、システムが提供すべき主要な機能コンセプトとドメインモデルを明確にしたい。
-   **操作例**: `goose-sdd --system "主要な機能として、ドキュメント自動生成、既存ドキュメントの同期、コードとの乖離検知を提供する。"`
-   **結果**: AIが意図を解釈し、`concept.yaml` レシピの文脈で `docs/sdd/01_system_concept.md` に関連内容が記述・生成される。
### ユースケース3: システムアーキテクチャの定義
-   **利用者**: テックリード、ソフトウェアアーキテクト
-   **状況**: プロジェクトの技術スタック、ディレクトリ構成、アーキテクチャパターンを定義したい。
-   **操作例**: `goose-sdd --system "クリーンアーキテクチャを採用し、主要なレイヤーを定義する。バックエンドはGo言語とGinフレームワーク、データベースはPostgreSQLを使用する。"`
-   **結果**: AIが意図を解釈し、`architecture.yaml` レシピの文脈で `docs/sdd/02_system_architecture.md` に関連内容が記述・生成される。
### ユースケース4: プロジェクトルールの定義・変更
-   **利用者**: 開発チームのメンバー
-   **状況**: チームでの議論の結果、コードの行数制限を80文字から120文字へ変更することが決定した。
-   **操作例**: `goose-sdd --system "コーディング規約を更新し、1行の最大文字数を120文字に変更してください。AIとの協働プロトコルも明記する。"`
-   **結果**: AIが意図を解釈し、`rule.yaml` レシピの文脈で `docs/sdd/03_project_rules.md` ファイル内の関連する規約が更新される。
### ユースケース5: ドメイン用語集の定義
-   **利用者**: ドメインモデラー、開発者
-   **状況**: プロジェクトで使用する主要なドメイン用語とそのコード上の命名規則を定義したい。
-   **操作例**: `goose-sdd --system "ドメイン用語として「顧客」をCustomer、「注文」をOrderと定義し、それぞれのコード名を指定する。"`
-   **結果**: AIが意図を解釈し、`glossary.yaml` レシピの文脈で `docs/sdd/04_domain_glossary.md` に関連内容が記述・生成される。
## 機能要件
| ID | 要件 | 詳細 |
|---|---|---|
| FR-1 | 自然言語によるインテント入力 | `--system` コマンドの引数として、開発者の意図（Intent）を自然言語の文字列で受け付けることができる。 |
| FR-2 | **対象レシピの特定とドキュメントへのマッピング** | 入力されたインテントの内容をAIが分析し、最も関連性の高いレシピ（`architecture.yaml`, `rule.yaml` など）を特定できる。さらに、特定されたレシピが管理するドキュメント（`docs/sdd/02_system_architecture.md` など）を正確にマッピングできる。 |
| FR-3 | ドキュメントの生成・更新 | 特定したレシピとマッピングされたドキュメントに対し、インテントに基づいた内容の追記、修正、または新規作成を行うことができる。これには以下のドキュメントが含まれる。<br>- `docs/sdd/00_product_background.md` (プロダクト背景)<br>- `docs/sdd/01_system_concept.md` (システムコンセプト)<br>- `docs/sdd/02_system_architecture.md` (システムアーキテクチャ)<br>- `docs/sdd/03_project_rules.md` (プロジェクトルール)<br>- `docs/sdd/04_domain_glossary.md` (ドメイン用語集) |
| FR-4 | 意図解釈の精度 | AIは、入力された自然言語の意図を正確に解釈し、適切なレシピを選択し、関連するドキュメントコンテンツを生成・更新する必要がある。 |
## 非機能要件
| ID | 要件 | 詳細 |
|---|---|---|
| NFR-1 | パフォーマンス | コマンド実行後、標準的なインテントであれば短時間内にドキュメントの更新処理を完了すること。 |
| NFR-2 | ユーザビリティ | - CLIから直感的に使用できること。<br>- 多少の表現の揺らぎ（例：「更新して」「変更して」）があっても、AIが柔軟に意図を汲み取り、適切なレシピを選択できること。 |
| NFR-3 | 信頼性 | 同じ、または類似したインテントに対して、常に一貫性のあるドキュメント変更が行われること。 |
