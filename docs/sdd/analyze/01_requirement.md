# 要求仕様書: Analyze Layer

## 概要

Analyze Layer は、`goose-sdd` における Reverse SDD の作業領域である。  
既存コード、設定、外部解析結果、人間が持つ断片情報を整理し、システムや機能の現状を説明可能な AS-IS ドキュメントとして再構成することを目的とする。

Analyze Layer は単なるコード要約機能ではない。  
コード由来の事実と、人間由来の曖昧情報を分離して扱い、それらを人間レビュー可能な単位で統合し、将来の Forward SDD や改善判断へ接続するための基盤である。

## 背景・目的

`goose-sdd` は、`Spec -> Code` だけでなく `Code -> Spec` も扱うことで、既存プロダクトにも SDD を途中導入できることを目指している。

既存開発では、次の課題が繰り返し発生する。

- コードは存在するが、背景、意図、制約、機能境界が説明できない
- ドキュメントが古い、または断片化しており、信頼できる現状理解がない
- AI によって変更速度は上がるが、理解負債が蓄積しやすい
- To-Be を定義する前に As-Is を正確に把握できず、机上設計になりやすい

Analyze Layer の目的は、これらの課題に対して以下を実現することにある。

- 既存コードベースから code-backed facts を回収し、現状理解の土台を作る
- Notion、Confluence、会話、記憶などのモザイク情報を真実と混同せず整理する
- `gather` と `mosaic` の成果を `synthesize` で統合し、AS-IS ドキュメントを形成する
- AS-IS を起点に、今後どこを正式な SDD 文書へ昇格させるか判断できる状態を作る
- ドキュメントとコードの乖離を、人間がレビュー可能な形で把握しやすくする

## ユースケース / ユーザーストーリー

### ユースケース 1: 既存システムの現状把握

- 開発者として、既存コードベースの構造と主要な責務を把握したい
- そうすることで、変更前に現実の実装を誤解せずに済む

### ユースケース 2: 特定機能の AS-IS 回復

- 開発者として、特定の機能についてコードや設定から現状仕様を回復したい
- そうすることで、要求や設計を更新する前提となる現状理解を作れる

### ユースケース 3: 断片情報の安全な整理

- 開発者として、会話や外部文書に散在する情報を利用したい
- ただし、その情報をコード由来の事実と分離し、未確認情報として扱いたい

### ユースケース 4: AS-IS から To-Be への接続

- 開発者として、回復した AS-IS をもとに、どこを `--system` や `--feature` に昇格させるべきか判断したい
- そうすることで、既存開発を無理なく SDD 運用へ移行できる

### ユースケース 5: 乖離と問題の発見

- 開発者として、コードと既存ドキュメントの矛盾や、構造上の違和感を早期に見つけたい
- そうすることで、今後の `cure` や Forward SDD の着手点を明確にできる

## 機能要件

### 1. Analyze Layer の初期化

- `--analyze init <language>` により、`docs/sdd/analyze/` の作業領域を初期化できること
- 出力言語設定に従って、Analyze Layer の文書を継続的に生成・更新できること

### 2. システム全体の探索

- `discover` により、プロジェクト全体の構造、主要な構成要素、問題意識の起点を把握できること
- システム全体の Reverse SDD の入口として機能すること

### 3. 解析対象スコープの定義

- `feature <feature>` により、解析対象となる機能または領域を定義できること
- システム全体だけでなく、特定機能単位で Analyze Layer を運用できること

### 4. コード由来の事実収集

- `gather <feature>` により、コード、設定、実行環境、外部解析コマンドの出力などから code-backed facts を収集できること
- 解析対象やプロジェクト特性に応じて、利用する解析手段を固定しすぎず選択可能であること
- `gather` の成果は、後続の統合やレビューに利用できる形で記録されること

### 5. モザイク情報の整理

- `mosaic <feature>` により、人間が持つ断片情報や外部文書由来の情報を整理できること
- これらの情報は code-backed facts と区別され、未確認または確認済みの状態を意識して扱えること

### 6. 情報統合による AS-IS 生成

- `synthesize <feature>` により、`gather` と `mosaic` の成果を統合して AS-IS ドキュメントを生成できること
- 統合時には、事実と仮説を混同せず、人間が確認・修正可能な形で整理されること

### 7. 正式 SDD への昇格判断支援

- `elevate <feature>` により、AS-IS をそのまま確定仕様とせず、どこを正式な SDD 文書へ昇格させるか検討できること
- Analyze Layer は、`--system` や `--feature` への入力となる判断材料を提供できること

### 8. 人間レビュー可能な粒度の維持

- 各コマンドは 1 テーマ単位で役割が分割されていること
- 一括生成ではなく、必要箇所のみ再実行・再検討できること

### 9. 継続的な現状同期の支援

- Analyze Layer は、一度きりの逆生成ではなく、コードとドキュメントの乖離を定期的に再確認する用途に使えること
- 継続運用の中で、局所的な As-Is の更新に対応できること

## 非機能要件

### 1. 信頼性

- コード由来の事実と人間由来の曖昧情報を明確に分離して扱うこと
- 未検証の情報を自動的に真実または正式仕様として確定しないこと

### 2. レビュー容易性

- 生成・更新される内容は、人間が段階的にレビュー、修正、承認しやすい粒度であること
- 大きな一括生成に依存せず、会話的に改善できること

### 3. 再実行容易性

- 同じコマンドを再実行して、現状に追従した文書更新ができること
- 一部の分析結果のみ差し替えたり、補完したりできること

### 4. 運用継続性

- 既存プロダクトへの途中導入が可能であること
- 重すぎる儀式を要求せず、現場の開発フローに組み込みやすいこと

### 5. 拡張性

- `gather` は特定ツールに強く固定されず、プロジェクトごとの解析コマンドや汎用解析ツールを取り込めること
- 対象システムや機能の特性に応じて、解析観点を差し替えられること

### 6. トレーサビリティ

- Analyze Layer の成果が、今後の `--feature`、`--system`、`--cure` で参照可能な形で残ること
- AS-IS の理解が、To-Be の検討や改善施策へ接続できること
