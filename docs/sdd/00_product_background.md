# Product Background

## 1. Product Context (Why): ビジネス背景

- **対象ユーザー**:
    - 従来の開発手法において、ドキュメントの陳腐化やコードとの乖離に悩むソフトウェア開発者および開発チーム。
    - AIを活用した開発を推進したいが、品質維持やコンテキスト管理に課題を感じているチーム。
- **解決する課題**:
    - **ドキュメントの陳腐化 (Dead Docs)**: ドキュメントが実装に追従できず、信頼性を失う問題。
    - **高コストな手動同期**: 人間がドキュメントとコードの一貫性を維持するために費やす、多大な時間と負担。
    - **AI開発の弊害**: AIが生成したコードが文脈から切り離され、結果として技術的負債を加速させる問題。
- **解決しないこと (現時点)**:
    - ビジネス要件そのものの定義。
    - 最終的な意思決定の完全自動化。

このプロジェクトは、`docs/sdd/` ディレクトリを**唯一の信頼できる情報源 (Source of Truth)** として位置づけます。しかし、それは静的なドキュメントではありません。

-   **交渉の場 (Negotiation Border)**: `docs/sdd/` は、**人間の「理想（Intent）」**と**AIが解析したコードの「現実（Reality）」**が出会い、合意形成を行う場です。
-   **結果整合性 (Eventual Consistency)**: コードとドキュメントは一時的に乖離（Drift）することを許容しつつ、`goose-sdd` を介した対話サイクルによって、最終的な整合性を維持します。

## 2. System Concept (What): システム概要

`goose-sdd` のコマンドは、情報の流れる方向（ベクトル）によって大別されます。

### A. 処方的コマンド (Prescriptive Commands)
**人間 (Intent) → AI → コード (Reality)**
人間が「こうあるべき（To-Be）」という意思をAIに伝え、コードや構成を変更させるためのコマンド群です。

-   **`--system <intent>`**: プロジェクト全体のアーキテクチャやルールを定義・変更します。 (`background`, `concept`, `architecture`, `rules`, `glossary`)
-   **`--feature <intent>`**: 特定機能の要件を定義し、実装を進めます。 (`requirements`, `design`, `tests`, `code`)

### B. 記述的コマンド (Descriptive Commands)
**コード (Reality) → AI → ドキュメント (Intent)**
AIが「こうなっている（As-Is）」という事実を観測し、人間に報告（ドキュメント化）するためのコマンド群です(構想段階)。

-   **`--analyze [target]`**: 指定されたコードを解析し、現状の仕様を `docs/sdd/` に反映します。

### C. 支援ツール (Tool Commands)
開発者を補助するためのコマンド群です。

-   **`--tool ask`**: `docs/sdd` の内容を知識ベースとして、プロダクトに関する質問応答を行います。

## 3. Development Process: 対話のサイクル (The Negotiation Loop)

`goose-sdd` を用いた開発は、以下のループを回すことで、ドキュメントを「生きた状態」に保ちます。

1.  **Drift (乖離)**: 開発が進み、コード（現実）とドキュメント（理想）の間にズレが発生します。
2.  **Analyze (分析)**: `goose-sdd --analyze` でAIがコードの現状を調査し、ドキュメントとの差分を提示します (Bottom-up)(構想段階)。
3.  **Review & Intent (判断と指示)**: 人間がAIの報告をレビューし、「バグ修正」や「仕様変更」などの新たな意思を `--feature` や `--system` 等で指示します (Top-down)。
4.  **Convergence (収束)**: 指示に基づきコードとドキュメントが再び一致し、新たなベースラインが確立されます。

## 4. 現状と主な特徴 (Current Status and Key Features)
-   **実行環境 (Runtime Environment)**: 主要スクリプト (`bin/goose-sdd`) は**Denoランタイム**への移行を完了し、パフォーマンスとセキュリティを向上させています。
-   **拡張性 (User Extensibility)**: `setup` コマンドにより、ユーザーはレシピを拡張して独自のMCPを追加できます。これにより、多様な開発ワークフローへの柔軟な適応が可能です。

## 5. 将来構想 (Future Vision)

本プロジェクトが目指す、より長期的なゴールです。

### 1. Agentic Workflow / Automation (自律化・自動化)

開発ワークフローそのものをAIエージェントが自律的に実行し、人間の介入を最小限に抑えることを目指します。

- **Test-Fix Loop (自律修正ループ)**:
- 「テスト実行 → 失敗検知 → エラーログをAIにフィードバック → コード修正」というサイクルを、テストがパスするまで自律的に繰り返すループ処理を実装します。
- **Validation Loop (ドキュメント整合性チェック)**:
- ドキュメント間の論理的な整合性をAI自身が検証し、採点や修正案の提示を行う自動レビュー機能を導入します。

### 2. Living Documentation (同期・維持)

コードとドキュメントが常に同期された「生きた状態」を維持するための仕組みを強化します。

- **Diff Detection & Sync (差分検知による逆同期の自動化)**:
- `git diff` などを利用して「コードのみが変更されたファイル」を自動検知し、関連するドキュメントだけをピンポイントで更新する機能を実装します。
- **CI/CD Integration**:
- GitHub ActionsなどのCI/CDパイプラインと連携し、Pull Request作成時に「ドキュメントとコードの乖離」を自動でチェックし、レポートする機能を提供します。

### 3. 外部サービス連携 (Integration)

- Notion, Confluence, Backlog といった外部ドキュメント管理サービスと連携し、`docs/sdd/` の内容を自動で同期・エクスポートする機能。
### 4. 自律的なコード品質維持 (Autonomous Code Quality Maintenance)

技術的負債を継続的に解消するための自律型エージェント機能を導入します。

- **第1段階: 診断 (Diagnosis) - `analyze` コマンドの進化**:
  - ルール違反、未使用のコード、過度に複雑なコードなどを特定し、診断レポートを生成します。
- **第2段階: 治療 (Treatment) - `refactor` コマンドの実装**:
  - 診断された問題を、ドキュメントファーストの原則に基づき、関連する仕様書を更新してからクリーンなコードを再生成することで修正します。
- **第3段階: 自律改善 (The Gardener) - `janitor` ループの実装**:
  - CI/CDパイプライン上で軽微な改善点を自律的に修正し、Pull Requestを生成することで、コードベースを継続的に改善します。
