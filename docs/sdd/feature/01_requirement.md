# 要求仕様書: `goose-sdd --feature` コマンド
## 概要
`goose-sdd` の `--feature` コマンドは、特定の機能開発における要求仕様、設計、テスト、コードの各段階を一貫して管理するための処方的コマンドです。AIを活用し、人間の「意図（Intent）」に基づき、`docs/sdd/` ディレクトリ配下のドキュメント群（特に `01_requirements.md`, `02_design.md`, `03_tests.md`, `04_code.md`）を生成・更新することで、ドキュメントの陳腐化を防ぎ、コードとの整合性を維持します。
## 背景・目的
従来のソフトウェア開発において、ドキュメントはしばしば実装との乖離や陳腐化の問題を抱え、その手動での同期には多大なコストがかかっていました。また、AIを活用した開発では、生成されたコードが文脈から切り離され、技術的負債を増加させるリスクがあります。
`--feature` コマンドは、これらの課題を解決し、以下の目的を達成します。
*   **ドキュメントの信頼性向上**: `docs/sdd/` を唯一の信頼できる情報源とし、機能開発の初期段階から最終的な実装まで、ドキュメントとコードの一貫性を保ちます。
*   **開発効率の向上**: AIを開発プロセスに統合することで、人間が定義した要求仕様に基づき、設計、テスト、コード生成を効率的に支援します。これにより、手動でのドキュメント更新やコード生成にかかる時間と労力を削減します。
*   **技術的負債の抑制**: AIが生成する成果物が`docs/sdd/`のコンテキストに深く基づくことで、文脈から切り離されたコードの生成を防ぎ、長期的な保守性を高めます。
*   **「交渉の場」の提供**: 人間の意図とAIが解析したコードの現実が対話的に収束するプロセスを促進し、開発チーム全体での合意形成を支援します。
## ユースケース / ユーザーストーリー
### ユースケース1: 新規機能の要求仕様定義
**アクター**: プロダクトマネージャー、ビジネスアナリスト、開発者
**シナリオ**: 新しい機能のアイデアが生まれた際、プロダクトマネージャーやビジネスアナリストは、`goose-sdd --feature <feature_name> requirements` のようなコマンドを通じて、この機能の初期要求を定義します。AIは、提供された意図に基づいて `01_requirements.md` の初期ドラフトを生成し、人間はそれをレビュー・修正することで、正式な要求仕様書を作成します。
### ユースケース2: 既存機能の要求仕様更新
**アクター**: 開発者
**シナリオ**: 開発中に、既存機能の要求に変更が生じた場合、開発者は `goose-sdd --feature <feature_name> requirements` コマンドを再度実行し、更新された意図をAIに伝えます。AIは既存の `01_requirements.md` との差分を分析し、変更点を提案、または人間との対話を通じてドキュメントを更新します。
### ユースケース3: 要求仕様に基づく次フェーズへの移行
**アクター**: 開発者
**シナリオ**: `01_requirements.md` が確定した後、開発者は `goose-sdd --feature <feature_name> design` コマンドを実行し、定義された要求仕様に基づいて機能の設計フェーズに進みます。AIは、要求仕様書の内容を基に `02_design.md` の作成を支援します。
## 機能要件
*   指定された機能名に基づいて、`docs/sdd/<feature_name>/01_requirements.md` ファイルを新規作成または更新できること。
*   `sdd.yaml` および `docs/sdd/00_product_background.md` の内容を考慮し、初期ドラフトを生成できること。
*   ユーザーからの入力（プロンプト）に基づき、要求仕様書の内容を更新できること。
*   機能要件、非機能要件、ユースケース、背景・目的などの標準的なセクションを含むMarkdown形式のドキュメントを生成できること。
*   多言語設定 (`docs/sdd/language`) に従って、適切な言語でドキュメントを生成できること。
## 非機能要件
*   **応答性能**: ユーザーがストレスなく対話できる程度の応答速度でドキュメントの生成・更新が行えること。
*   **一貫性**: `docs/sdd/` ディレクトリ内の他のドキュメント（例: `sdd.yaml`, `00_product_background.md`）との用語や表現の一貫性が保たれること。
*   **堅牢性**: 不正な入力や予期せぬ状況に対しても、適切なエラーハンドリングを行い、システムがクラッシュしないこと。
*   **拡張性**: 将来的な要件定義プロセスの変更や、新しいドキュメント形式への対応が容易であること。
